# CineTube Windows 운영 서버 구성 작업계획

- 작성일: 2026-09-13
- 작업 예정일: 2026-09-14
- 상태: 사용자 요청으로 다음 날 진행. 이 문서는 계획이며 서버 설정은 아직 적용하지 않음.

## 1. 확인된 환경

- 현재 PC는 클라이언트이며 작업 저장소는 `D:\workspace\cinetube`이다.
- 운영 서버는 내부망에 있는 별도의 Windows PC이다.
- 사용자가 서버 실행을 확인했다.
- 원격 접속 방식은 아직 구성되지 않았으며 최초 설정부터 필요하다.
- 요청 범위는 원격 접속, 배포 환경, 운영 환경, 모니터링 환경 및 보안 강화이다.
- 저장소에는 Python API, 별도 Worker, PostgreSQL 구성과 기본 헬스체크·로그 관련 코드가 있다. 실제 서버의 설치 상태는 별도 확인해야 한다.
- 현재 문서는 로그인 없는 로컬 서비스 기준이므로 운영 접근 통제를 검토해야 한다.

## 2. 시작 전 확인

1. 서버의 Windows 버전·에디션, 내부 IP, 컴퓨터 이름을 확인한다.
2. 서버 프로젝트 설치 경로, 실행 계정, 현재 실행 방식과 포트를 확인한다.
3. 서버 PC에서 직접 초기 설정할 수 있는지와 관리자 권한 사용 가능 여부를 확인한다.
4. 클라이언트 IP 및 서버 접속을 허용할 사용자·PC 범위를 확인한다.
5. 서버·클라이언트 주소 고정 또는 DHCP 예약 가능 여부를 확인한다.
6. 현재 DB·이미지 저장 위치, 데이터 용량, 백업 위치를 확인한다.

비밀번호·개인키는 대화나 저장소에 기록하지 않는다.

## 3. 진행 순서

### 1단계: 원격 관리 연결

- 서버에서 OpenSSH Server 지원·설치 상태를 확인하고 배포·관리용 SSH를 구성한다.
- 클라이언트 공개키를 서버 관리 계정에 등록하고 키 인증 접속을 검증한다.
- 접속 검증 후 비밀번호 인증 제한을 적용하고 재접속을 확인한다.
- Windows 방화벽의 SSH 접근 범위를 허용한 클라이언트로 제한한다.
- GUI 관리가 필요하면 Windows 에디션의 RDP 호스트 지원 여부를 확인한 뒤 NLA 및 접근 제한을 적용한다.
- 공유기 외부 포트 개방 없이 내부망에서 구성한다.
- 접속 차단 시 서버에서 직접 복구할 절차를 확보한 상태로 설정을 변경한다.

완료 기준: 클라이언트에서 서버에 키 인증으로 접속할 수 있고, 허용 범위 밖의 접근 제한 및 재접속을 검증했다.

### 2단계: 현황 점검과 보안 강화

- 변경 전 코드·설정·DB·이미지를 백업한다.
- 서비스 실행 계정과 관리 계정을 구분하고 필요한 파일 권한만 부여한다.
- PostgreSQL은 서버 내부 연결로 제한하고 불필요한 인바운드 포트를 차단한다.
- 로그인 및 서버 측 관리자 권한 검사를 설계·적용한다.
- 내부 접속 주소와 인증서 신뢰 배포 방식을 정한 뒤 HTTPS를 구성한다.
- 브라우저 및 기존 확장 프로그램의 사용 출처를 확인하여 CORS를 제한한다.
- 운영 비밀 설정을 저장소 밖에서 관리하고 파일 접근 권한을 제한한다.
- 실제 사용 흐름으로 로그인·조회·등록·이미지 접근을 검증한다.

완료 기준: 비인가 관리 요청이 차단되고, 허용된 사용자는 HTTPS로 필요한 기능을 사용할 수 있다.

### 3단계: 배포 및 운영 구성

- 개발·운영 설정과 데이터를 분리한다.
- 현재 서버 구조에 맞는 Windows 서비스 관리 방식을 선정한다.
- 웹·API·Worker·DB의 자동 시작, 시작 순서, 장애 재시작을 구성한다.
- 테스트 → 버전별 배포 → 상태 확인 → 실패 시 롤백 절차를 구성한다.
- DB 스키마 변경은 코드 롤백과 구분하여 백업·복구 절차를 마련한다.
- DB와 이미지 파일의 정기 백업, 보존 기간, 서버 외부 백업 위치를 정한다.
- 별도 복구 위치에서 실제 복원과 데이터·이미지 일관성을 확인한다.

완료 기준: 재부팅 후 서비스가 복구되고, 배포·롤백 및 백업 복원 절차를 검증했다.

### 4단계: 모니터링 및 장애 대응

- 웹·API 응답, DB 연결, Worker 진행 상태와 작업 적체를 점검한다.
- CPU·메모리·디스크 여유 공간과 로그 증가량을 확인한다.
- 오류·응답 지연·로그인 실패·백업 실패를 기록한다.
- 로그 순환 및 보존 기간을 구성한다.
- 알림 수신 방식과 임계값은 사용자와 결정하고, 승인된 채널로 장애 알림을 검증한다.
- 서버 전체 중단을 감지할 별도 점검 위치의 필요성을 검토한다.
- 접속 방법, 배포·복구 명령, 로그 위치, 장애 대응 절차를 운영 문서에 기록한다.

완료 기준: 장애를 의도적으로 재현하여 감지·기록·알림·복구 흐름을 확인했다.

## 4. 다음 작업 시작점

서버 PC에서 직접 작업 가능한지 확인한 뒤 Windows 버전·에디션, 서버 내부 IP, 프로젝트 설치 경로를 수집하고 원격 접속부터 구성한다. 현재 클라이언트 PC를 운영 서버로 설정하지 않는다.
